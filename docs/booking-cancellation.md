# ยกเลิกการจองและคืนมัดจำ 100 บาท

## ขอบเขต

- แอดมินยกเลิกทีละรายการ เฉพาะการจองที่ยืนยันแล้วและยังไม่ส่งมอบเครื่อง/คืนเครื่อง/ส่งไฟล์
- คืนเฉพาะมัดจำ 100 บาท ไม่ใช่มูลค่าจองรวม ระบบ **ไม่โอนเงินอัตโนมัติ**
- ลูกค้าเห็นสถานะในประวัติการจอง ไม่ส่งข้อความยกเลิกหรือคืนเงินไปที่ LINE
- ไม่รวมลูกค้ายกเลิกเอง ยกเลิกทั้งคอนเสิร์ต ย้ายรอบ คืนบางส่วน หรือยกเลิกแบบไม่คืนมัดจำ
- เก็บยอดเดิม รายละเอียดอุปกรณ์ สลิป และผลตรวจสลิปไว้ ห้ามนำการจองที่ยกเลิกกลับมายืนยันอีก

## ติดตั้งก่อนใช้งาน

1. สำรองฐานข้อมูล และทดสอบใน Supabase สำหรับ staging ก่อน
2. รัน `scripts/add_booking_cancellation.sql` ใน Supabase SQL Editor **ก่อน deploy โค้ด** โดยใช้สิทธิ์เจ้าของฐานข้อมูล
3. SQL เพิ่มตาราง/RPC/trigger และ bucket ส่วนตัว `refund-proofs` ไม่ยกเลิกการจอง ไม่คืนเงิน และไม่ปรับจำนวนสต็อกเดิม รันซ้ำได้
4. ใช้โครงสร้างฐานข้อมูลของโปรเจ็กต์ปัจจุบัน: bookings ต้องมีคอลัมน์มัดจำ, SlipOK, เลนส์ และ fulfillment แล้ว รวมถึง admin_users/admin_audit_log อย่ารัน migration เก่าย้อนหลังทับ RPC รุ่นล่าสุด
5. Deploy โค้ด แล้วทดลองด้วยข้อมูลทดสอบ: ยกเลิก → รับงาน → โอนทดสอบเอง → บันทึกหลักฐาน ตรวจประวัติลูกค้า ยอดสรุป สต็อก และประวัติแอดมิน

ไม่ต้องเพิ่ม env สำหรับฟีเจอร์นี้ ใช้สิทธิ์แอดมินและ Supabase service role เดิม หากยังไม่ติดตั้ง SQL การจองปกติยังอ่านได้ แต่ปุ่มยกเลิกจะแจ้งให้ติดตั้ง ไม่ควรเปิดใช้จนผ่าน staging

การติดตั้งจริงและการโอนเงินจริงไม่ได้รวมอยู่ในชุดทดสอบในเครื่อง

## วิธีใช้งาน

1. หน้าแอดมิน → การจอง → รายการยืนยันแล้ว → **ยกเลิก — คืนมัดจำ 100 บาท**
2. ตรวจรายการและหลักฐานรับมัดจำ ระบุเหตุผล ติ๊กยืนยัน แล้วกดยกเลิก สถานะเป็น **ยกเลิกแล้ว — รอคืนมัดจำ 100 บาท** เครื่องและเลนส์จะไม่ถูกนับจองในรายการนี้อีก
3. กด **รับงานคืนมัดจำ 100 บาท** ให้สำเร็จก่อนโอน แอดมินคนอื่นจะรับงานซ้อนกันไม่ได้ ควรใช้บัญชีแอดมินแยกคน ไม่แชร์บัญชีกัน
4. ตรวจบัญชีรับเงินกับลูกค้าและโอนคืนเอง 100 บาท
5. ใส่เลขอ้างอิงธุรกรรมจริง แนบภาพโอนคืน JPG/PNG/WebP ไม่เกิน 5 MB ติ๊กว่าโอนแล้ว แล้วกด **บันทึกคืนมัดจำแล้ว 100 บาท**
6. ตรวจสถานะล่าสุดว่าเป็น **คืนมัดจำแล้ว** หลักฐานเปิดดูได้เฉพาะแอดมินผ่านลิงก์อายุ 5 นาที ลูกค้าเห็นเฉพาะสถานะและเวลาบันทึก ไม่เห็นบัญชีธนาคาร เหตุผลภายใน หรือชื่อแอดมิน

หลักฐานคืนเงินเป็นการบันทึกโดยแอดมิน ไม่ได้ส่งตรวจ SlipOK หรือยืนยันกับธนาคารอัตโนมัติ ต้องตรวจผู้รับและยอดเงินจริงก่อนบันทึก เลขอ้างอิงเดียวกันใช้บันทึกคืนเงินให้สองการจองไม่ได้

## ข้อควรระวังเมื่อเกิดปัญหา

- รายการมัดจำไม่ใช่ 100 บาท หรือผลตรวจสลิปไม่ตรง จะถูกบล็อก ไม่เดายอดจากราคามือถือปัจจุบัน
- รายการเก่าที่มัดจำเป็น NULL จะผ่านได้เฉพาะเมื่อมีผลตรวจสลิปสำเร็จ 100 บาท ห้ามแก้ยอดย้อนหลังเพื่อให้ผ่านโดยไม่มีหลักฐาน
- หาก timeout หรือไม่แน่ใจว่าบันทึกสำเร็จ ให้โหลดสถานะล่าสุดและตรวจบัญชีธนาคาร **ห้ามโอนซ้ำ** การลองบันทึกซ้ำไม่เขียนทับหลักฐานที่สำเร็จแล้ว
- งานคืนเงินที่รับไว้ไม่มีหมดอายุอัตโนมัติ เพื่อป้องกันคนอื่นรับต่อแล้วโอนซ้ำ
- คืนงานได้เฉพาะเจ้าของงานที่ยืนยันว่า **ยังไม่ได้โอนและไม่มีการโอนค้าง** ถ้าโอนไปแล้วให้บันทึกหลักฐาน ไม่คืนงาน
- หากผู้รับงานเข้าใช้บัญชีไม่ได้ ให้ประสานเจ้าของร้าน ตรวจธนาคารและหลักฐานก่อนแก้ไขโดยผู้ดูแล ห้ามลบบัญชีผู้รับงานระหว่างงานค้างหรือปลดล็อกโดยเดาว่ายังไม่โอน
- ข้อมูลยกเลิกและหลักฐานต้องเก็บไว้ การลบ booking ที่มีประวัติคืนเงินจะถูกฐานข้อมูลป้องกันไว้ การย้อนกลับเวอร์ชันแอปไม่ควรลบตารางหรือเปลี่ยน cancelled กลับเป็น confirmed
- หากบันทึกหลักฐานเจอความผิดพลาดเครือข่าย ระบบอาจเก็บไฟล์ที่ยังไม่มีการอ้างถึงไว้โดยตั้งใจ ห้ามลบทันที เพราะรายการคืนเงินอาจบันทึกสำเร็จแล้วแต่คำตอบมาไม่ถึง

## ผลกับยอดและระบบเดิม

- มูลค่าจองรวมยังรวมเฉพาะ confirmed จึงไม่รวมรายการยกเลิก แต่ไม่แก้ total_amount เดิมเป็นศูนย์
- มัดจำรับสะสม (ก่อนหักคืน) = มัดจำของรายการยืนยัน + มัดจำของรายการยกเลิกในระบบนี้
- มัดจำรอคืนรวมทั้ง pending และ processing; มัดจำคืนแล้วแสดงแยก ไม่ถือว่าเป็นยอดจองใหม่
- เมื่อมีรายการยกเลิก ยอดเงินทุกช่องอ่านด้วย RPC เดียวจาก snapshot เดียว เพื่อไม่ให้นับรอคืนและคืนแล้วซ้ำระหว่างเปลี่ยนสถานะ
- รายการเก่าที่ยัง confirmed และ deposit_amount เป็น NULL ยังไม่นับในมัดจำรับสะสมตามพฤติกรรมเดิม ควรตรวจสอบหลักฐานก่อนแก้ข้อมูลย้อนหลัง
- ไม่บวกสต็อกเครื่อง/เลนส์หรือโควตารอบ การคืนสิทธิ์จองใช้ query นับเฉพาะสถานะ active ที่มีอยู่แล้ว
- สลิปต้นฉบับและเลขอ้างอิงไม่ถูกล้าง ป้องกันนำสลิปเดิมไปจองซ้ำ
- ถ้าตั้ง SHEETS_WEBHOOK_URL ไว้ จะส่งสถานะและข้อมูลคืนเงินเพิ่มเติมผ่าน webhook เดิมแบบ best-effort หลังบันทึกฐานข้อมูลสำเร็จ Google Apps Script ภายนอกอาจต้องปรับเองหากต้องการคอลัมน์คืนเงิน ฐานข้อมูลและประวัติในเว็บเป็นแหล่งอ้างอิงหลัก

## ตรวจสอบในเครื่อง

```sh
npm test
npx tsc --noEmit --incremental false
npm run build
```

ชุดทดสอบใช้ PostgreSQL จำลองในหน่วยความจำ (PGlite), เรียก SQL migration/RPC จริง และทดสอบ API/การแสดงผลด้วยบริการจำลอง ไม่อ่านข้อมูลหรือโอนเงินจริงใน Supabase ไม่ส่ง LINE ทดสอบสิทธิ์ ลองซ้ำ เจ้าของงาน หลักฐาน สต็อก เลนส์ และสลิปเดิม รวมถึงการป้องกันไฟล์แม้มี storage policy เดิมที่เปิดกว้าง

การทดสอบในเครื่องไม่แทนการทดสอบบน Supabase staging โดยเฉพาะเครือข่าย Storage และการทำงานพร้อมกันหลาย connection

ระหว่างติดตั้งเครื่องมือทดสอบ npm รายงานช่องโหว่ dependency 20 รายการ (1 low, 2 moderate, 16 high, 1 critical) ยังไม่ได้ตรวจแยกผลกระทบหรืออัปเกรดแพ็กเกจอื่นในงานนี้ ควรตรวจเป็นงานแยกก่อนใช้งานจริง ไม่ควรรัน audit fix แบบบังคับโดยไม่ทดสอบระบบเดิม
