# โค้ดส่วนลด

## กติกาที่ใช้

- ลดเป็นจำนวนเงินบาทเต็มจากยอดรวมมือถือและเลนส์ **ต่อการจอง** ใช้ได้ทุกคอนเสิร์ต
- แต่ละบัญชีที่ล็อกอินใช้โค้ดเดิมได้ครั้งเดียว อิง user_id ที่ผูกกับ LINE ไม่อิงเบอร์ที่กรอก
- แอดมินกำหนด **จำนวนสิทธิ์รวม** ต่อโค้ดได้ (เว้นว่าง = ไม่จำกัด โค้ดเดิมทุกตัวยังไม่จำกัด) นับ 1 สิทธิ์ต่อการจอง/บัญชี
  - นับทั้งรายการที่แนบสลิปแล้ว และรายการของบัญชีอื่นที่ **กำลังกันเครื่องอยู่** (เหมือนการกันสต็อก) เพื่อไม่ให้หลายคนกันพร้อมกันแล้วได้สิทธิ์เกินจำนวน
  - hold หมดเวลาหรือถูกปล่อยก่อนแนบสลิป คืนสิทธิ์ทันที ส่วนสิทธิ์ที่ใช้แล้วไม่คืน แม้ยกเลิก ลบการจอง หรือสลิปถูกปฏิเสธ (ตัดสินใจ 31 ต.ค. 2569: ลูกค้าที่ถูกปฏิเสธส่งสลิปใหม่ได้เสมอโดยโควต้าไม่เกิน ถ้าถูกกินสิทธิ์ด้วยสลิปปลอม ให้แอดมินเพิ่มจำนวนสิทธิ์เอง)
  - ลดจำนวนสิทธิ์ต่ำกว่าที่ใช้ไปแล้วได้ จะหยุดรับการใช้ใหม่ทันที แต่รายการที่กันไว้แล้วยังจ่ายได้จนหมดเวลา hold
  - สิทธิ์เต็มระหว่างลูกค้ากรอกข้อมูล หน้าเว็บจะแจ้งและนำโค้ดออกให้ เพื่อจองต่อด้วยราคาปกติ
- ใช้ได้หนึ่งโค้ดต่อการจอง ไม่ลดมัดจำ และยอดสุทธิห้ามต่ำกว่ามัดจำ
- เวลาเริ่มรวมจุดเริ่มต้น เวลาหมดอายุไม่รวมจุดสิ้นสุด: `starts_at <= เวลาปัจจุบัน < expires_at` แบบฟอร์มแอดมินใช้เวลาไทยเสมอ
- ตัวอย่าง: ค่าเครื่องและเลนส์รวม 600 บาท โค้ดลด 50 บาท → สุทธิ 550 บาท มัดจำ 100 บาท ชำระตอนรับเครื่อง 450 บาท

## สิทธิ์แต่ละช่วง

| ขั้นตอน | ผลต่อสิทธิ์ |
| --- | --- |
| กดใช้โค้ดในหน้ากรอกข้อมูล | ตรวจเงื่อนไขและแสดงยอด ยังไม่ใช้สิทธิ์ |
| กดต่อไปหน้าโอนเงิน | กันสต็อกและส่วนลดพร้อมกัน เก็บยอดที่ยอมรับไว้กับการจอง |
| ย้อนกลับจนปล่อย hold หรือ hold หมดเวลาโดยยังไม่แนบสลิป | ใช้สิทธิ์ได้อีก หากโค้ดยังเปิดและไม่หมดอายุ ไม่ต้องรอ cron |
| แนบสลิปและสร้างรายการรอตรวจสำเร็จ | ใช้สิทธิ์กับรายการนี้แล้ว |
| สลิปถูกปฏิเสธ | แก้สลิปในรายการเดิมได้ ส่วนลดเดิมยังอยู่ จองรายการใหม่ด้วยโค้ดเดิมไม่ได้ |
| ยืนยันแล้วมายกเลิก ไม่ว่าจะคืนมัดจำหรือไม่คืน | ไม่คืนสิทธิ์โค้ด สต็อกคืนตามระบบยกเลิกเดิม |
| ลบรายการจองที่ใช้สิทธิ์แล้ว | ประวัติการใช้ยังอยู่ ไม่ทำให้ใช้โค้ดซ้ำได้ |

เมื่อกันส่วนลดสำเร็จแล้ว การแก้จำนวนส่วนลด พัก ลบ หรือหมดอายุของโค้ด ไม่เปลี่ยนยอดเดิมภายในเวลาของ hold การกดกันรายการเดิมซ้ำไม่ต่อเวลา หลัง hold หมดอายุต้องตรวจเงื่อนไขใหม่ หากโอนแล้วแต่ทำรายการไม่สำเร็จให้ติดต่อร้าน ไม่โอนซ้ำ

แอดมินแก้เลนส์ของรายการยืนยันแล้วได้ตามระบบเดิม โดยคงจำนวนส่วนลดไว้และคิดส่วนต่างราคาเลนส์ หากยอดใหม่ต่ำกว่ามัดจำ ระบบปฏิเสธการแก้ไข มัดจำและการตรวจ SlipOK ยังอ้างยอดมัดจำเดิม

## หน้าจัดการ

เปิดหน้าแอดมิน → **โค้ดส่วนลด** เพื่อสร้าง แก้ไขวันเวลา/จำนวนส่วนลด พัก เปิด ลบ และดูประวัติการใช้

- รหัสใช้ A–Z, 0–9, `_`, `-` ยาว 3–32 ตัว ไม่แยกตัวพิมพ์เล็ก/ใหญ่
- รหัสที่สร้างแล้วเปลี่ยนชื่อรหัสไม่ได้ แต่แก้ชื่อโปรโมชันได้
- การลบหยุดรับการใช้ใหม่ และเก็บประวัติไว้ ดูได้จาก “แสดงโค้ดที่ลบแล้ว” รหัสที่ลบแล้วสร้างซ้ำไม่ได้
- ปุ่มพัก/เปิดเปลี่ยนเฉพาะสถานะ ไม่เขียนราคา/วันเวลาทับจากหน้าที่อาจค้างอยู่
- การ์ดโค้ดแสดง “ใช้สิทธิ์แล้ว X / Y” พร้อมแถบความคืบหน้า จำนวนที่เหลือ และจำนวนที่กำลังกันเครื่องอยู่ ป้ายสถานะขึ้น “สิทธิ์เต็ม” เมื่อใช้ครบ
- “ยอดส่วนลดที่ใช้” รวมรายการที่ส่งสลิปแล้วทุกสถานะ แยกยอดเฉพาะการจองยืนยันแล้วให้ด้วย ไม่รวม hold ที่ยังไม่ส่งสลิป
- ยอดในหน้าสรุปการจองเดิมใช้ยอดสุทธิหลังลด มัดจำยังแยกตามเดิม
- ประวัติแอดมินบันทึกการสร้าง แก้ไข พัก/เปิด และลบพร้อมค่าก่อนแก้
- ไม่มีข้อความ LINE เพิ่มสำหรับการใช้โค้ดหรือการยกเลิก ข้อความอนุมัติเดิมเพิ่มรายละเอียดส่วนลดและแสดงยอดสุทธิ
- Google Sheets ได้ `total_amount` เป็นยอดสุทธิ ใช้โครงสร้าง webhook เดิม

## อัปเดตฐานข้อมูลก่อน deploy

1. ตรวจว่าฐานข้อมูลมีโครงสร้างปัจจุบันของโปรเจ็กต์ รวมระบบ hold, เลนส์, update-slip, ยกเลิก และ admin audit แล้ว สำรองข้อมูลและลองใน staging ก่อน
2. รันไฟล์ **`supabase/migrations/20261031121133_booking_discount_codes.sql` แล้วตามด้วย `supabase/migrations/20261031124225_harden_discount_checkout.sql` ทั้งไฟล์ตามลำดับ** ใน Supabase SQL Editor ด้วยสิทธิ์เจ้าของฐานข้อมูล **ก่อน deploy โค้ดรุ่นนี้** ทั้งสองไฟล์ใช้ transaction และรันซ้ำได้ โดยไม่คำนวณราคาการจองเดิมทับ หากติดตั้งไฟล์แรกแล้ว ให้รันเฉพาะไฟล์ hardening เพิ่ม
   - **โควต้าสิทธิ์รวม:** รัน `supabase/migrations/20261031160000_discount_code_quota.sql` ต่อจากสองไฟล์ข้างบน ก่อน deploy โค้ดที่มีช่องจำนวนสิทธิ์ ไฟล์นี้เพิ่มคอลัมน์ `max_uses` (โค้ดเดิมเป็น NULL = ไม่จำกัด) ไม่แก้การจองหรือประวัติเดิม รันซ้ำได้ และเก็บ RPC บันทึกโค้ดรุ่นเดิมไว้ หน้าแอดมินที่ยังไม่โหลดใหม่จึงยังบันทึกได้โดยไม่ลบโควต้าที่ตั้งไว้
3. ไม่ต้องนำสคริปต์เก่าใน `scripts/` มารันทับ RPC ปัจจุบัน ไฟล์ใหม่เรียกใช้ RPC hold เดิมและเพิ่ม RPC สำหรับส่วนลดแยกต่างหาก
4. Deploy โค้ดแล้วโหลดหน้าแอดมินและหน้าลูกค้าใหม่ จึงสร้างโค้ดจากแท็บโค้ดส่วนลดได้ ไม่มีโค้ดตัวอย่างถูกสร้างให้อัตโนมัติ และไม่ต้องเพิ่ม env
5. หากใช้ระบบ migrations ผ่าน Supabase CLI อยู่แล้ว ให้ตรวจประวัติ migration ของโปรเจ็กต์ก่อนใช้ workflow นั้น อย่าใช้ `db reset` กับฐานข้อมูลจริง

**ห้าม deploy โค้ดก่อน SQL** เพราะหน้าประวัติ รายการแอดมิน และข้อความอนุมัติอ่านคอลัมน์ส่วนลดใหม่ด้วย หากต้องย้อนเวอร์ชันแอป ให้คง migration และประวัติส่วนลดไว้ ไม่ลบตาราง/trigger หรือรัน SQL เก่าย้อนทับ ราคาสุทธิของรายการเดิมยังถูกเก็บไว้ แต่หน้ารุ่นเก่าจะไม่มีรายละเอียดโค้ด

ไฟล์ hardening ปิดสิทธิ์เขียน bookings และอัปโหลด/แก้สลิปตรงจาก Supabase browser roles ให้ผ่าน API ของเว็บเท่านั้น พร้อมล็อกสต็อกระหว่างบันทึกสลิปครั้งแรก หน้าเว็บนี้ใช้ service_role ฝั่ง API อยู่แล้ว หากมีแอปอื่นนอก repository ที่เขียนฐานข้อมูลหรือ bucket slips ตรงด้วย authenticated token ต้องย้ายแอปนั้นมาใช้ API ด้วย

หากเคยรันไฟล์ hardening รุ่นแรกแล้วพบ `42501: must be owner of table objects` ให้เปิดไฟล์ฉบับแก้ล่าสุดและรันทั้งไฟล์ใหม่ใน SQL Editor ด้วย role `postgres` ไม่ต้องเปลี่ยนเจ้าของตาราง: Supabase เปิด RLS บน `storage.objects` ไว้แล้วและให้จัดการ policy ได้ แต่ไม่ให้ `ALTER TABLE` ตารางนี้ ฉบับแก้ตรวจว่า RLS เปิดอยู่แทนการเปิดซ้ำ และยังสร้าง policy ป้องกันสลิปเหมือนเดิม ถ้ารันทั้งไฟล์เดิมเป็น transaction เดียวแล้วล้มเหลว คำสั่งก่อนหน้าจะไม่ถูก commit

ผล audit และประเด็น dependency ที่ยังต้องแก้แยกอยู่ใน `docs/discount-security-review.md` การผ่านชุดทดสอบฟีเจอร์ไม่ได้แปลว่าปิดประกาศช่องโหว่ของ dependency แล้ว

## การตรวจสอบ

คำสั่งในเครื่อง:

```powershell
npm test
npx tsc --noEmit --incremental false
npm run build
```

`tests/discount-database.test.mjs` ใช้ PostgreSQL ใน PGlite แยกจากข้อมูลจริง โหลด RPC hold/เลนส์/ยกเลิก/เปลี่ยนสลิปจริงร่วมกับ migration ใหม่ ตรวจการใช้ซ้ำ สต็อก ยอดขั้นต่ำ ประวัติ การหมดเวลา สิทธิ์ฐานข้อมูล และการเรียกซ้ำ ส่วน `tests/discount-api.test.mjs` ตรวจ auth, CSRF, การไม่เชื่อราคาจากลูกค้า การอัปโหลดซ้ำ และยอดใน Sheets/LINE ด้วย mock ไม่เรียกบริการภายนอก

PGlite ใช้การเชื่อมต่อเดียว จึงไม่ได้แทนการทดสอบโหลดพร้อมกันหลาย connection บน Supabase จริง และการ render UI แบบอัตโนมัติไม่ได้แทนการกดใช้งานบนมือถือจริง

ก่อนเปิดให้ลูกค้าใช้ ให้ทดสอบบน staging ด้วยบัญชีทดสอบ:

1. มือถือจอแคบและคอมพิวเตอร์: สร้างโค้ด กรอกโค้ด แสดงยอดรวม/มัดจำ/ส่วนที่เหลือ และวันเวลาไทย
2. สองแท็บของบัญชีเดียวใช้โค้ดเดียวกันพร้อมกัน ต้องสร้างการใช้สิทธิ์สำเร็จครั้งเดียว บัญชีอื่นยังใช้โค้ดได้
3. ปล่อย hold หมดเวลาแล้วเริ่มใหม่ ใช้ได้เมื่อโค้ดยังไม่หมดอายุ; ใช้โค้ดหมดอายุ/พัก/ลบกับรายการใหม่ไม่ได้
4. ยืนยันการจองแล้วแก้เลนส์ ส่วนลดต้องคงเดิม; กรณียอดหลังเอาเลนส์ออกต่ำกว่ามัดจำต้องถูกปฏิเสธ
5. ยกเลิกทั้งคืนและไม่คืนมัดจำ ตรวจยอดมัดจำ สต็อก และประวัติ โค้ดต้องใช้ซ้ำกับรายการใหม่ไม่ได้
6. จองไม่ใส่โค้ด ตรวจสลิป อนุมัติ และดูประวัติ ทำงานตามเดิม

การพัฒนารอบนี้ไม่รัน migration กับฐานข้อมูลจริง ไม่ deploy และไม่ส่ง LINE หรือข้อมูลไป Google Sheets จริง
